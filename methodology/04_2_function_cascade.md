# Этап 4.2. Каскадирование задач и функций

## Цель и границы

Проверить согласованность задач и функций по организационной цепочке внутри
одного документа: сверху вниз — кому назначено выполнение, снизу вверх —
с какой задачей или функцией родителя связано действие исполнителя.

На входе — объекты и организационные связи из
[этапа 2](02_entity_extraction.md), записи деятельности
с условиями и источниками из [этапа 3](03_activity_extraction.md).
Ни объекты, ни функции, ни контекст из других документов не используются.
Это описание методологии, а не реализация или схема БД.

Базовый результат — связи между задачами и функциями и два признака аномалий:
родительская функция без дочерних и дочерняя функция без родительской.
Коллизии функций объектов одного уровня рассматриваются на этапе 4.1.

## 1. Группа и направление связей

Группа состоит из организационного объекта уровня N и его непосредственных
исполнителей уровня N+1. Например, департамент и его отделы, затем каждый
отдел и его должности. Уровни определяются установленными организационными
связями, а не одинаковыми названиями должностей или глубиной разделов текста.

Внутри группы сопоставляем задачи и функции родителя с задачами и функциями
исполнителей. Далее для краткости называем их родительскими и дочерними
функциями. Подчинённость объекта ограничивает поиск, но не назначает ему
функции автоматически. Неизвестные и неоднозначные организационные связи
требуют уточнения; на их основании не объявляем отсутствие пары.

У одной родительской функции может быть несколько дочерних. У каждой
дочерней функции может быть только одна родительская. Это правило относится
к связям функций: функцию не связываем сразу с несколькими основаниями.
Одна функция промежуточного уровня может быть ребёнком на предыдущем шаге
и родителем на следующем.

## 2. Поиск по эмбеддингам

Сравниваем полные формулировки задач и функций внутри группы. В представление
для поиска включаем контекст действий: название и специализацию объекта,
само действие, предмет и результат, условия, ограничения и временную роль.
Используем только сведения текущего документа, сохраняя исходные цитаты
отдельно. Одного сходства названий подразделений недостаточно.

Для каждой дочерней функции оцениваем сходство со всеми допустимыми
родительскими функциями группы и выбираем максимальное. Если технический
поиск возвращает лишь часть записей, он должен обеспечивать нахождение
лучшего кандидата; отсутствие результата поиска не заменяет проверку группы.

Пороги применяются к одной зафиксированной метрике сходства и одному способу
подготовки эмбеддингов. Процент сходства не является вероятностью правильности
связи. Модель, метрику и способ вычисления оценки сохраняем с результатом.

## 3. Выбор единственного родителя

Решение принимается по лучшему кандидату для каждой дочерней функции:

| Максимальное сходство | Действие |
|---|---|
| Выше 85% | Автоматически принять связь, без LLM |
| Выше 50%, до 85% включительно | Передать выбранную связь на верификацию LLM |
| 50% и ниже либо допустимых кандидатов нет | Пары нет, в LLM не отправлять |

Таким образом, ровно 85% требует верификации, ровно 50% означает отсутствие
пары. Пороги проверяем до округления оценки для отображения.

Другие кандидаты не становятся дополнительными родителями. После отклонения
лучшего кандидата LLM автоматически переходить к следующему не предусмотрено.
При точном равенстве максимальных оценок единственный победитель не установлен:
фиксируем неоднозначность для разрешения, не выбираем родителя произвольно
и не выдаём этот случай за отсутствие пары.

## 4. Верификация субагентами

Субагент получает батч из 10 вопросов; последний батч может быть меньше.
Один вопрос — одна выбранная пара родительской и дочерней функций.
В вопросе передаём уникальный `question_id`, обе записи и их объекты,
оценку сходства, контекст действий и исходные фрагменты документа.

LLM выдаёт только вердикт по предложенной связи: подтвердить или отклонить.
Она проверяет, действительно ли дочернее действие обеспечивает родительскую
задачу или функцию с учётом предмета, условий и ролей. Подготовка,
согласование, утверждение и контроль не взаимозаменяемы; при этом разные
действия могут быть связаны как задача и способ её выполнения.

Рассуждение обрабатываем нативным механизмом интерфейса отдельно от итогового
ответа, без извлечения JSON из свободного текста рассуждений. Итог принимаем
через `json_object`, например:

```json
{
  "answers": [
    {"question_id": "q1", "verdict": "confirmed"},
    {"question_id": "q2", "verdict": "rejected"}
  ]
}
```

Формат JSON сам по себе не гарантирует правильную структуру. Система проверяет
ровно один ответ на каждый переданный вопрос, отсутствие посторонних ID
и допустимость вердиктов. Пропуски, ошибки и некорректные ответы возвращаем
на повторную обработку; они не означают отклонённую связь или отсутствие пары.
LLM не назначает другого родителя, не добавляет функции и не формирует
отдельное заключение о превышении полномочий.

## 5. Итоговые связи и два направления проверки

Принимаем автоматические связи выше 85% и подтверждённые LLM связи.
По одному полученному набору связей выполняем обе проверки; отдельный
обратный выбор кандидатов не создаёт дополнительных родителей.

**Снизу вверх:** у каждой дочерней функции должен быть единственный принятый
родитель. Если кандидатов выше 50% нет, ставим «пара не найдена». Если лучший
кандидат отклонён LLM, ставим «пара не подтверждена». Оба случая означают,
что у дочерней функции нет принятого основания, но сохраняют разные причины.

**Сверху вниз:** у каждой функции, для которой проверяется передача ниже,
должна быть хотя бы одна принятая дочерняя функция. Родитель может остаться
без детей не только из-за низкого сходства, но и потому, что для всех
кандидатов выиграли другие родители либо связи были отклонены LLM.

Незавершённую верификацию, равенство лучших оценок и неполные входные данные
помечаем отдельно. Пока они могут изменить результат, отсутствие принятой
связи не считаем окончательно установленной аномалией.

## 6. Аномалии базового каскада

| Признак | Статус для пользователя | Интерпретация |
|---|---|---|
| Родительская функция без дочерних | Исполнитель не найден | Возможный пробел в распределении функций |
| Дочерняя функция без родительской | Основание не найдено | Возможное превышение полномочий |

Это признаки для проверки, а не доказанные нарушения. Отсутствие основания
в каскаде само по себе не доказывает превышения полномочий: документ может
прямо закреплять самостоятельное действие за исполнителем. Наличие связи
также не доказывает полное покрытие всех частей родительской функции.
Базовый алгоритм не оценивает частичное покрытие и не проверяет отдельно
все запреты и исключительные полномочия.

Проверку применяем только к ожидаемым переходам каскада. У верхнего объекта
не требуем родителя за пределами рассматриваемой структуры, у конечного
исполнителя — дочерних функций. Если документ явно закрепляет действие
лично за текущим уровнем без передачи ниже, отсутствие детей не аномалия;
основание исключения сохраняем с цитатой. Если сам документ не описывает
нужный уровень исполнителей, отмечаем недостаток данных.

## 7. Сохранение результата и контрольные примеры

Для каждого решения сохраняем текущий документ и группу, ID функций
и объектов, лучшего кандидата и его оценку, способ решения (автоматический
или LLM), вердикт, принятую связь либо причину её отсутствия, статус обработки
и источники записей. Для неоднозначности сохраняем всех лучших кандидатов.
Источники должны вести в текущий документ и содержать точные цитаты.

Для аномалии отсутствия сохраняем также состав проверенной группы и состояние
обработки: одной цитатой нельзя доказать, что подходящей пары нет.

| Ситуация | Ожидаемый результат |
|---|---|
| Две дочерние функции выбрали одну родительскую с оценками 91% и 89% | Обе связи приняты автоматически, у родителя два ребёнка |
| У дочерней функции кандидаты с оценками 88% и 87% | Единственный родитель — кандидат с 88% |
| Лучший кандидат имеет оценку 85% | Один вопрос LLM; связь зависит от вердикта |
| Лучший кандидат имеет оценку 50% | Пары нет, LLM не вызывается |
| Кандидат с 80% отклонён, следующий имеет 75% | Пара не подтверждена; автоматического перехода ко второму нет |
| Все дети выбрали другие функции родителя | У оставшейся родительской функции нет исполнителей |
| Ответ субагента на вопрос отсутствует | Ошибка обработки; вывод об аномалии пока не готов |
| У функции конечной должности нет детей | Не аномалия: передача ниже не ожидается |

Повторяем процедуру для соседних уровней и собираем цепочки вида
«задача департамента → функция отдела → действие исполнителя».
Итог описывает распределение, закреплённое документом, а не фактическое
поведение сотрудников.
