# Этап 1. Парсинг документа и разбиение на разделы и пункты

## Цель и границы этапа

Восстановить структуру каждого документа: разделы, подразделы, пункты,
подпункты и списки. Сохранить весь исходный текст и его порядок, чтобы на
следующем этапе передавать выделенные секции ИИ-модели вместе с контекстом.

На этом этапе не извлекаем отдельные функции, не назначаем исполнителей,
не строим организационную иерархию и не сравниваем редакции. Принадлежность
секции к компании, департаменту или должности определяется при последующем
смысловом разборе.

## Входные данные

Методология применяется к одному документу или комплекту произвольного
количества документов. Тип документа, предметная область, наличие редакций
и конкретная система нумерации не заданы заранее. Положения, инструкции,
регламенты и другие документы проходят один и тот же процесс определения
структуры.

Каждый документ обрабатываем независимо. Совпадение номеров пунктов между
документами не означает совпадения содержания. Номер редакции сохраняем,
если он известен; его отсутствие не препятствует обработке.

Два предоставленных положения о внутреннем аудите используются как примеры
и контрольные материалы. Их названия, разделы и подразделения не задают
обязательные правила парсинга других документов.

## 1. Подготовка текста

Сохраняем оригинал без изменений. Адаптер входного формата извлекает текст
и доступные признаки структуры: абзацы и стили, страницы, отступы, таблицы,
листы и ячейки. Для сканов сначала требуется распознавание текста. Если
адаптер или распознавание недоступны, фиксируем невозможность извлечения,
а не выдаём пустой документ за успешно разобранный.

Универсальность методологии означает общий процесс после извлечения текста;
она не означает, что один регекс читает любой бинарный формат. Для таблиц
сохраняем границы строк и ячеек, для документов без нумерации используем
заголовки, оформление и другие доступные признаки.

Извлечённое текстовое представление фиксируем как `original_text` и дальше
не изменяем. Для текстового файла это его исходное содержимое; для Word,
PDF или таблицы — результат извлечения, связанный с позициями в оригинальном
файле. Для распознавания структуры создаём рабочую копию, в которой
нормализуем переносы строк и технические пробелы, учитываем разметку.

Формулировки, номера и порядок фрагментов сохраняем. Нормализация не должна
исправлять содержание или удалять значимые символы. Для каждого выделенного
фрагмента сохраняем положение в `original_text` и доступную привязку к
оригинальному файлу. Смещения в рабочей копии нельзя выдавать за смещения
в исходном представлении. Если привязка к странице или ячейке недоступна,
её не придумываем.

Реквизиты, оглавление и блок приложений выделяем отдельно от основного текста.
Оглавление сохраняем как служебный блок: его заголовки не должны повторно
попадать в дерево содержательных разделов. Если приложение только упомянуто,
сохраняем это упоминание, не предполагая наличие его текста.

## 2. Определение профиля документа с помощью ИИ

Перед разбиением агент одним начальным вызовом изучает документ и возвращает
JSON-объект с профилем парсинга. Если документ помещается в контекст модели,
передаём его целиком. Иначе передаём большой репрезентативный набор фрагментов:
начало, середину, конец, примеры разных стилей заголовков, списков и таблиц.
Отмечаем позиции фрагментов и пропуски между ними, чтобы модель не воспринимала
выборку как сплошной текст. Одного начала документа недостаточно для вывода
о структуре всего файла.

Агент определяет наблюдаемые способы оформления и нумерации, предлагает
регулярные выражения и правила вложенности. Результат — конфигурация
парсера, а не пересказ документа или извлечённые функции.

Профиль содержит:

- версию формата профиля и поддерживаемый движок регулярных выражений;
- паттерны заголовков, пунктов и списков, область их применения и приоритет;
- способ определения уровня: глубина номера, стиль заголовка или отступ;
- правила служебных блоков и обработки склеенных пунктов, если они обнаружены;
- положительные и отрицательные примеры совпадений;
- позиции изученных фрагментов и нерешённые вопросы.

Пример JSON для документа с десятичной нумерацией; показано одно правило,
остальные добавляются по наблюдаемой структуре документа:

```json
{
  "profile_version": 1,
  "regex_engine": "python_re",
  "strategy": "numbering",
  "patterns": [
    {
      "id": "decimal_clause",
      "node_type": "clause",
      "regex": "^(?P<marker>[0-9]+(?:\\.[0-9]+)+)\\.[ \\t]+",
      "flags": ["MULTILINE"],
      "apply_to": "block_start",
      "hierarchy": "marker_depth",
      "priority": 10,
      "positive_examples": ["5.3. Директоры", "5.3.1. Обеспечивают"],
      "negative_examples": ["В соответствии с п. 5.3. настоящего документа"]
    }
  ],
  "service_rules": [],
  "unresolved": []
}
```

В рабочем профиле дополнительно сохраняем фактически изученные диапазоны
текста. Словари стратегий, областей применения и правил вложенности задаёт
пайплайн; модель выбирает поддерживаемые значения. Стратегии могут опираться
на нумерацию, оформление, таблицы или их сочетание. Наличие в документе
десятичных номеров не является обязательным условием.

Ответ в формате `json_object` проверяем по схеме: наличие полей, типы,
допустимые значения. Затем компилируем регексы выбранным движком и проверяем
их на примерах и дополнительных фрагментах, не использованных при подборе,
если такие фрагменты есть. Проверяем ложные границы, пропуски и конфликты
правил. Положительные примеры самой модели не заменяют проверку по исходнику.
Выполнение регексов ограничиваем по времени; произвольный код из ответа
модели не исполняем.

Один начальный вызов — штатный сценарий, а не гарантия достаточности для
любого файла. Если далее обнаружен другой способ оформления или профиль
не прошёл проверку, сохраняем проблемный фрагмент и запрашиваем адресное
уточнение профиля либо отмечаем необходимость проверки. Нераспознанные
фрагменты не удаляем. Утверждённый профиль сохраняем вместе с документом.

## 3. Распознавание структурных границ

Пайплайн применяет проверенный профиль ко всему документу. Регулярные
выражения и признаки оформления выделяют кандидатов на начало, например:

- раздела: `5. Права и обязанности`;
- нумерованного пункта или подраздела: `5.3.`, `5.3.1.`;
- буквенного подпункта: `а.`, `б.`;
- маркированного списка;
- ненумерованного заголовка.

Границы проверяем по окружающему тексту, нумерации и оформлению. Одного
совпадения с числовым шаблоном недостаточно: дата или ссылка «в соответствии
с п. 3» не открывает новый пункт. Выделение жирным также само по себе не
доказывает, что весь выделенный фрагмент является заголовком.

Поиск внутри строк включаем для правил, которым это требуется: несколько
пунктов или заголовок следующего раздела могут быть склеены с предыдущим
текстом. Паттерны начала строки автоматически не превращаем в поиск
номеров по всему тексту.

## 4. Построение дерева

Родителя определяем по правилам профиля. При десятичной нумерации:

- `5.3.1` относится к `5.3`;
- `5.3` относится к разделу `5`;
- раздел `5` относится к документу.

Узел может одновременно содержать собственный текст и дочерние элементы.
Буквенные и маркированные подпункты связываем с соответствующим списком и
его вводной фразой. Повторение буквы внутри другого списка допустимо.

Пример структуры редакции 9, с сокращёнными текстами для наглядности:

```text
5. Права и обязанности
└── 5.3. Директоры департаментов и Директоры направлений ДИТААД и ДОА:
    ├── 5.3.1. обеспечивают стратегическое управление…
    ├── 5.3.2. организуют … руководство … проверок:
    │   └── Список
    │       ├── а. аудит ИТ систем… (ДИТААД)
    │       └── б. аудит процессов развития… (ДОА)
    └── 5.3.3. готовят предложения…
```

При другом оформлении используем уровни заголовков, отступы или структуру
таблицы согласно профилю. Документ без разделов может содержать текстовые
блоки верхнего уровня; отсутствующую иерархию не создаём искусственно.
Ненумерованные заголовки сохраняем в соответствующем месте документа.
Если родитель или граница неоднозначны, сохраняем фрагмент и отмечаем
необходимость проверки. Пропущенные пункты и заголовки не придумываем.

## 5. Присоединение текста

Текст после структурного маркера относится к этому элементу до следующей
подтверждённой границы. Перенос строки сам по себе новый пункт не создаёт.

Вводный текст родительского пункта сохраняем отдельно от текстов дочерних
пунктов. Продолжения и заключительные абзацы после списков также сохраняем
в исходном порядке; при необходимости они становятся текстовыми узлами.

Предложения внутри пункта не разбиваем на отдельные функции и не
переформулируем. В частности, формулировку «не имеют права» сохраняем в
родительском пункте: она понадобится модели при разборе вложенного списка.

## 6. Примеры особенностей и контрольные случаи

Эти случаи взяты из предоставленных положений. Они проверяют общие правила,
но не ограничивают входной комплект и не задают жёсткие шаблоны для всех
документов.

| Случай | Правило обработки |
|---|---|
| Пункты `3.10`, `3.11`, `3.12` редакции 9 находятся внутри одной строки | Выделить отдельные пункты, проверив границы по нумерации и тексту |
| `10.Контроль качества` приклеен к предыдущему абзацу | Выделить самостоятельный раздел, не требовать пробела после номера |
| В п. `9.3` два списка начинаются с `а` | Сохранить две группы с собственными вводными фразами и порядком элементов |
| В конце документа повторяются названия разделов в оглавлении | Сохранить оглавление как служебный блок без повторного создания разделов |
| Пункт `5.5.3` редакции 8 содержит только `;` | Сохранить пункт и отметить отсутствие содержательного текста |
| Внутри предложения встречается ссылка на другой пункт | Оставить ссылку частью текста, не открывать новый пункт |

Дополнительно проверяем документы без нумерации, с другими алфавитами
маркеров, с таблицами и со сменой оформления внутри файла. Для каждого
поддерживаемого формата нужны примеры с известным ожидаемым разбиением.

## 7. Формат результата

Результат для каждого документа — отдельное дерево, которое храним в
SQLite. Для передачи модели или интерфейсу его можно собрать в JSON.
На уровне документа сохраняем имя исходного файла, формат, редакцию при
наличии и профиль парсинга.

Для узла достаточно следующих полей:

| Поле | Содержание |
|---|---|
| `type` | Раздел, пункт, заголовок, список, элемент списка, таблица, строка, ячейка, текстовый или служебный блок |
| `marker` | Номер или маркер, например `5.3.2` или `а`; при отсутствии — `null` |
| `text` | Собственный текст узла, без повторного включения текста дочерних элементов |
| `children` | Дочерние элементы в исходном порядке |
| `source` | Позиции в `original_text` и доступная привязка к оригинальному файлу; диапазон родителя может включать детей |

Номер или буква не являются глобальным идентификатором. Элемент определяется
документом и положением в дереве; два подпункта `а` в разных списках остаются
разными элементами. Замечания о пустых пунктах и неоднозначных границах
сохраняем рядом с результатом со ссылками на соответствующие узлы.

## 8. Проверки и передача на следующий этап

Этап завершён, когда:

1. Весь исходный текст учтён в содержательных или служебных блоках.
2. Сохранены порядок фрагментов и исходная нумерация.
3. Каждый дочерний элемент находится у соответствующего родителя.
4. Оглавление не создало дубликатов содержательных разделов.
5. Каждый узел можно найти в оригинале по сохранённым позициям.
6. Пустые пункты и неразрешённые неоднозначности явно отмечены.
7. Профиль прошёл проверку JSON, регексов и качества разбиения по исходнику.
8. Проверены применимые контрольные случаи, включая особенности формата
   и структуры конкретного документа.

На следующий этап передаём секцию с её дочерними элементами и контекстом
родителей. Например, для подпункта `5.3.2.а` доступна цепочка
`5 → 5.3 → 5.3.2 → список → а` с вводными текстами. Выбор размера секций
для вызовов модели и извлечение из них функций в JSON относятся к следующему
этапу методологии.

## 9. Структура SQLite

Ниже зафиксирована предлагаемая структура хранения для первого этапа
методологии под SQLite 3.38+ с включёнными JSON-функциями. В backend уже
существуют ORM-модели `Document` и `Clause` в `src/la_rp_peace/models.py`. Приведённый SQL —
самостоятельная схема для методологии, а не миграция этих моделей;
существующий API пока с ней не связан. При интеграции нужно сопоставить
документы с `Document`, узлы с `Clause` и сохранить используемые API
идентификаторы. Два параллельных хранилища в рабочем приложении не требуются.

Исполняемая схема находится в [01_document_parsing.sql](01_document_parsing.sql).
Она создаёт три таблицы в отдельном файле БД, например `methodology.sqlite3`:

| Таблица | Назначение | Основные поля |
|---|---|---|
| `documents` | Один исходный документ | `id`, `file_name`, `source_format`, `revision`, `original_text`, `source_map`, `parsing_profile`, `parse_status`, `created_at` |
| `document_nodes` | Все элементы дерева документа | `id`, `document_id`, `parent_id`, `position`, `node_type`, `marker`, `text`, `source_start`, `source_end` |
| `parsing_issues` | Замечания к документу или отдельному узлу | `id`, `document_id`, `node_id`, `issue_type`, `message`, `is_blocking`, `resolved_at`, `created_at` |

`documents.id` связывает документ с его узлами. `document_nodes.parent_id`
ссылается на родительский узел того же документа; для верхнего уровня это
`NULL`. Массив `children` отдельно не храним: получаем детей по `parent_id`
и сортируем по `position`. Позиции начинаются с 0 и уникальны среди соседей.
У каждого списка собственный узел, поэтому повторяющиеся подпункты `а`
принадлежат разным родителям.

Типы узлов: `section`, `clause`, `heading`, `list`, `list_item`, `table`,
`table_row`, `table_cell`, `text`, `service`. Названия соответствуют типам
из раздела 7. Реквизиты, оглавление и иные служебные блоки сохраняются как
`service`.

`source_format` не ограничен закрытым перечнем расширений; `revision`
допускает `NULL`. `parsing_profile` имеет тип `TEXT` и содержит проверенную
конфигурацию агента, примеры и изученные диапазоны. До получения профиля
значение — `NULL`. Проверка формы JSON-объекта в БД не заменяет проверку
полной схемы и работоспособности паттернов в приложении. JSON сериализуем
при записи и десериализуем при чтении; `json_valid()` и `json_type()`
проверяют корректность JSON и тип верхнего уровня. `source_map` также
хранится как JSON-текст. См. [JSON-функции SQLite](https://www.sqlite.org/json1.html).

Таблицы объявлены `STRICT`: идентификаторы и позиции имеют тип `INTEGER`,
тексты — `TEXT`. `id INTEGER PRIMARY KEY AUTOINCREMENT` присваивает ID при
вставке и предотвращает повторное использование ID удалённых записей.
Флаг `is_blocking` хранится как `INTEGER` со значениями `0` или `1`.
Временные метки храним в `TEXT` в UTC в формате ISO 8601, например
`2026-09-23T10:00:00.000Z`; приложение использует этот же формат для
`resolved_at`. См. [строгие таблицы SQLite](https://www.sqlite.org/stricttables.html).

`source_map` — JSON-массив соответствий диапазонов `original_text` позициям
в файле, например странице и абзацу или листу, строке и столбцу. Каждое
соответствие содержит `start`, `end` и `location` с доступными координатами.
Для обычного текстового файла отдельная карта может не требоваться: значение
`[]`, а смещения указывают прямо на текст. Сам бинарный оригинал сохраняется
существующим механизмом хранения файлов backend; в `original_text` помещаем
только его текстовое представление.

Диапазон источника задаём как `[source_start, source_end)` в символах Unicode
исходного текста, начиная с 0. Это не байтовые смещения и не индексы UTF-16.
Например, исходный фрагмент можно получить в SQLite так:

```sql
SELECT substr(d.original_text, n.source_start + 1,
              n.source_end - n.source_start) AS source_fragment
FROM document_nodes AS n
JOIN documents AS d ON d.id = n.document_id
WHERE n.id = :node_id;
```

`:node_id` — параметр идентификатора узла. Диапазон родителя может включать детей,
но поле `text` содержит только его собственный текст. Если текст продолжается
после списка, продолжение храним дочерним узлом `text` на соответствующей
позиции, чтобы сохранить порядок.

Статусы документа:

- `pending` — ожидает разбора;
- `parsed` — дерево сформировано, проверки ещё не завершены;
- `needs_review` — обнаружены неоднозначности, требующие проверки;
- `validated` — проверки завершены, открытых блокирующих замечаний нет.

БД проверяет существование документа и родителя, принадлежность родителя
тому же документу, уникальность позиции среди соседей и допустимость полей.
Ссылка узла на самого себя запрещена. На каждом соединении до начала
транзакции выполняем `PRAGMA foreign_keys = ON` и проверяем, что
`PRAGMA foreign_keys` возвращает `1`. Настройка одного соединения не
включает проверку для остальных. Это требуется и для составных внешних
ключей, и для каскадного удаления.
См. [внешние ключи SQLite](https://www.sqlite.org/foreignkeys.html).

Проверки всего дерева выполняет приложение перед присвоением `validated`:
отсутствие циклов из нескольких узлов, вложенность диапазонов, соответствие
порядка источнику, отсутствие потерянного текста, границы в пределах
`original_text` и отсутствие открытых блокирующих замечаний. SQL-схема сама
по себе не выполняет эти проверки и не переключает статусы автоматически.

Пустой пункт исходника может остаться неблокирующим замечанием, если его
границы и содержимое подтверждены. Неразрешённая граница или родитель —
блокирующее замечание. Разрешение замечания фиксируем через `resolved_at`.

При сохранении сначала создаём документ, затем узлы от родителей к детям,
после них замечания. Дерево и его итоговый статус записываем одной транзакцией.
После разбора исходный текст и карту позиций не изменяем: изменённый исходник сохраняем
отдельной записью документа, чтобы не нарушить ссылки на фрагменты.

На первом этапе для одного документа храним одно дерево. История повторных
разборов, функции и организационные сущности в эту схему пока не входят.
Удаление документа каскадно удаляет его дерево и замечания; удаление узла —
его поддерево и связанные замечания. Такое удаление должно быть явной
операцией приложения.

SQL-файл предназначен для однократного применения к новому файлу БД.
Команда выполняется из корня репозитория при наличии SQLite CLI:

```bash
sqlite3 -bail methodology.sqlite3 < methodology/01_document_parsing.sql
```

Путь `methodology.sqlite3` можно заменить путём к выбранной БД. Файл БД
содержит рабочие данные и не добавляется в репозиторий. Повторное применение
завершится ошибкой существующих таблиц без перезаписи данных. Создание
таблиц выполняется транзакционно; при ошибке вызывающая программа должна
остановиться и откатить транзакцию. В CLI это обеспечивает остановка
с `-bail` и закрытие соединения, в Python нужно вызвать `rollback()`.

Для проверки без файлов используем `sqlite3.connect(":memory:")` из
стандартной библиотеки Python и `executescript()` для SQL-файла. Новые
Python-зависимости для этого не нужны. Изменение схемы методологии само
по себе не переключает существующий backend на другую СУБД.
