# Этап 5.1. Сопоставление редакций и отображение изменений

## Цель и границы

Показать, какие фрагменты документа сохранились, изменились, переместились,
появились или были удалены между двумя редакциями. Результат отображается
как git diff: две стороны «До» и «После» с точным выделением изменений.

Сначала устанавливаем соответствие фрагментов, затем сравниваем их текст.
Пункт 4.1 может соответствовать пункту 6.5: номер не является постоянным
идентификатором между редакциями.

На входе — результаты [этапа 1](01_document_parsing.md).
Повторно документы не парсим. Этапы 2–4 не обязательны для построения diff:
контекст разделов и исполнителей берём из исходного текста. Исходные деревья,
объекты и записи каждого документа остаются независимыми; сопоставления
сохраняем отдельно и не переписываем ими результат извлечения.

Здесь не устанавливаем потерю функций, передачу ответственности или появление
коллизий. «Новый пункт» не обязательно означает новую функцию, а «удалённый
пункт» — потерянную функцию. Значение изменений анализируется далее.
Документ описывает методологию и логический результат, а не SQL-схему
или готовую реализацию API.

## 1. Загрузка и определение редакций

Пользователь загружает документы через «+» в веб-интерфейсе, не раскладывая
их вручную на «до» и «после». Система использует метаданные этапа 1:
название из шапки, организацию, предмет документа, номер редакции, даты
и другие реквизиты с источниками. Имя файла — дополнительная подсказка.

Сначала определяем, какие файлы являются редакциями одного документа.
Разные положения не становятся редакциями друг друга только из-за сходства
названий или разницы дат. ИИ может помогать сопоставить реквизиты и содержание;
неподтверждённое предположение не выдаём за установленную пару.

Затем определяем порядок «до → после» по согласующимся номерам редакций
и датам. Различаем дату утверждения, создания и вступления в силу;
дата загрузки и техническая дата файла не определяют порядок редакций.
Если нужных сведений нет или они противоречат друг другу, показываем причину
и просим пользователя подтвердить пару и порядок до окончательного сравнения.

На фронте всегда видны выбранные документы, редакции, даты и основание
автоматического выбора. Пользователь может поменять пару или порядок.
Выбор и его подтверждение сохраняем в рамках конкретного сравнения,
а не как неизменное свойство документа.

Одно сравнение связывает две редакции. При большем числе редакций система
предлагает соседние по установленному порядку; можно выбрать другую пару.
Методология не привязана к числу загруженных файлов или конкретному типу
положения. Сопоставление разных комплектов по функциям — отдельная задача.

## 2. Подготовка фрагментов из этапа 1

Используем полный `original_text`, дерево разделов и пунктов, `node_id`,
порядок узлов, позиции в тексте и доступную привязку к оригинальному файлу.
ID узлов двух документов независимы: их равенство или различие не определяет
соответствие фрагментов.

Единица сравнения — логический фрагмент: заголовок, пункт, абзац, элемент
списка или ячейка таблицы. Визуальный перенос строки на странице не создаёт
самостоятельного изменения. Для таблиц сохраняем контекст строки, столбца
и заголовков; для списков — общую вводную фразу.

Сравниваем весь извлечённый текст, включая реквизиты, оглавление, таблицы,
приложения и текст вне нумерованных пунктов. Собственный текст родителя
сравниваем отдельно от дочерних пунктов: включающий детей диапазон раздела
не должен повторно показывать их изменения. Структурные группировки служат
для навигации, а не для повторного подсчёта тех же изменённых символов.

Если участок плохо разбит на узлы, используем его диапазон исходного текста
с отметкой ограничения структуры. Если сам текст не извлечён или повреждён,
отмечаем неполноту, а не считаем участок пустым. Сравнение текста не является
сравнением шрифтов, изображений или оформления, не представленных этапом 1.

Для поиска готовим нормализованную копию: убираем распознанный номер пункта
и технические различия пробелов. Не удаляем числа внутри содержания, даты,
отрицания, сроки и другие значимые части. Оригинальный текст не меняем;
нормализованная копия не используется вместо него в итоговом diff.

## 3. Поиск соответствий

### 3.1. Точное совпадение

Код ищет совпадения нормализованного текста по всему документу. Это позволяет
найти неизменённый пункт, даже если его номер или раздел изменились.

Единственное совпадение с согласующимся контекстом может быть принято
автоматически. Если одинаковый текст встречается несколько раз или изменилась
вводная фраза, нужны дополнительные проверки. Например, строка «Подготавливает
отчёт» под разными исполнителями не получает произвольную пару.

### 3.2. Фуззи-поиск

Для остальных фрагментов код подбирает несколько кандидатов по сходству
слов и текста. Заголовки и соседние пункты помогают ранжировать кандидатов,
но не ограничивают поиск прежним разделом или номером пункта.

Оценка сходства служит для отбора, а не является вероятностью правильного
соответствия. Низкая оценка сама по себе не доказывает удаление или добавление.
Конкретную метрику и пороги выбирают и проверяют на контрольных примерах
при реализации; сохраняют их с версией способа сопоставления.

### 3.3. Проверка ИИ и поиск по смыслу

ИИ проверяет неоднозначных кандидатов с исходным текстом, заголовками,
вводными фразами, соседними пунктами и контекстом исполнителя с обеих сторон.
Для сильно переписанных фрагментов без подходящих фуззи-кандидатов выполняем
дополнительный поиск по смыслу. Агенту должен быть доступен релевантный текст
обеих редакций, а не только первоначальный короткий список кандидатов.

Проверяем также разделение, объединение и переработку блоков:

- один фрагмент → один;
- один → несколько;
- несколько → один;
- несколько → несколько, если переработан целый блок.

Сложное соответствие сохраняем группой, не придумывая однозначные пары
внутри неё. Уже найденное совпадение не должно скрывать возможное разделение:
проверяем оставшиеся фрагменты также на связь с сопоставленными блоками.

Агент возвращает структурированный JSON-объект: ссылки на предложенные
фрагменты обеих сторон, основание сопоставления, контекстные подтверждения
и неясные случаи. Текст документа является данными, а не инструкциями агенту.
Код проверяет принадлежность всех ссылок выбранным редакциям, диапазоны
и отсутствие конфликтующих принятых соответствий.

В окончательном результате один диапазон текста не участвует одновременно
в нескольких противоречащих друг другу сопоставлениях. Альтернативные
кандидаты остаются предложениями для проверки, а не отдельными изменениями.
Ошибка запроса не означает, что соответствие отсутствует.

## 4. Классификация результата

| Результат | Значение |
|---|---|
| Без изменений | Текст и структурное положение сохранились |
| Изменён | Есть различия исходного текста |
| Перенумерован | Изменился номер без самостоятельного переноса фрагмента |
| Перемещён | Фрагмент перенесён в другую часть структуры или изменён его относительный порядок |
| Разделён | Одному прежнему фрагменту соответствуют несколько новых |
| Объединён | Нескольким прежним фрагментам соответствует один новый |
| Переработан блок | Нескольким прежним фрагментам соответствуют несколько новых без надёжной попарной привязки |
| Новый пункт / фрагмент | Фрагмент «после» не имеет найденного соответствия в «до» |
| Удалённый пункт / фрагмент | Фрагмент «до» не имеет найденного соответствия в «после» |
| Требует проверки | Соответствие или характер изменения не установлен однозначно |

Характеристики могут сочетаться: «перемещён и изменён», «разделён
с изменениями». Статус проверки сохраняем отдельно от признаков изменения.
При изменении только номера показываем перенумерацию, не называя её
изменением содержания.

Разница номера или абсолютной позиции не доказывает перемещение: перед
пунктом могли добавить новые пункты. Учитываем соответствия родительских
разделов и относительный порядок соседей. Перенос целого раздела показываем
как групповое изменение, не объявляя каждый его пункт отдельным переносом.

Перед отметкой «новый» или «удалённый» проверяем перенос, переформулировку,
разделение и объединение по выбранным редакциям. Отсутствие результата
в ограниченном списке кандидатов недостаточно. Если поиск или извлечение
нужных участков не завершены, показываем «требует проверки» с причиной.

## 5. Точный текстовый diff

После принятия соответствий код сравнивает исходные фрагменты и выделяет
добавленные и удалённые диапазоны; замена представляется удалением старого
и добавлением нового текста. Для группы фрагментов сохраняем их порядок,
границы и привязку каждого диапазона к своему источнику.

ИИ помогает установить соответствие, но не переписывает текст для показа.
Изменения номеров, дат, формулировок и знаков остаются видимыми. Техническую
нормализацию, уже выполненную при извлечении этапом 1, не выдаём за доступную
для восстановления разницу оригинальных файлов.

Изменение вводного контекста показываем в соответствующем заголовке или
родительском фрагменте и даём перейти к нему из дочернего пункта. Одинаковый
текст дочернего пункта не доказывает неизменность его смысла при другой шапке.

## 6. Сохранение результата

Хранение рассчитано на SQLite; ниже логические данные без SQL-схемы.

Для сравнения сохраняем:

- `comparison_id`, `before_document_id`, `after_document_id`;
- основание выбора пары и порядка, источники реквизитов и подтверждение пользователя;
- версии результатов парсинга и способа сопоставления;
- статус выполнения, полноту охвата и ограничения.

Для блока сопоставления сохраняем:

- `change_id` и ссылку на сравнение;
- списки фрагментов «до» и «после»: `node_id`, диапазоны исходного текста и порядок;
- признаки изменения и статус необходимости проверки;
- способ и краткое основание сопоставления, источники контекста;
- точные добавленные и удалённые диапазоны для отображения diff.

У нового фрагмента список «до» пустой, у удалённого — пустой список «после».
У неоднозначного фрагмента отдельно храним кандидатов и причину неопределённости;
пустая сторона сама по себе не означает подтверждённое добавление или удаление.

Диапазоны задаём в символах Unicode как `[start, end)` относительно сохранённого
`original_text`, согласованно с этапом 1. Это не байты и не индексы UTF-16
JavaScript. Название документа, путь пункта и доступное положение в оригинале
система получает из источника; агент не придумывает номера страниц.

Результат привязан к конкретным версиям извлечения. Повторная обработка
не дописывает дубли блоков в тот же результат; новая версия сравнения
не затирает прежнюю незаметно. При изменении исходного дерева старые ссылки
не переназначаем по совпавшим номерам пунктов: требуется пересчёт зависимого diff.

## 7. Передача на фронт

Backend передаёт структурированные блоки, исходные тексты обеих сторон,
точные диапазоны выделения и ссылки на источники. Фронт отображает результат,
но не определяет соответствия самостоятельно и не извлекает их из объяснения ИИ.

В интерфейсе две колонки «До» и «После»:

- новый пункт — зелёным справа, слева нет прежнего фрагмента;
- удалённый — красным слева, справа нет нового фрагмента;
- изменённый — обе версии рядом с выделением конкретных изменений;
- перемещённый или перенумерованный — старый и новый путь;
- разделённый, объединённый или переработанный блок — группа связанных фрагментов;
- неоднозначный — отметка «Требует проверки» и причина;
- неизменившийся — сворачиваемый контекст.

Можно перейти к исходному месту документа с любой стороны. Разницу только
номера не смешиваем с изменением содержательной формулировки. Неполный
результат не показываем как окончательный. Счётчики считают уникальные блоки
сопоставления, а не число источников или кандидатов; пересекающиеся признаки
не складываем в общее количество изменений как независимые события.

## 8. Контрольные примеры

Примеры условные и не задают шаблон конкретного документа.

| До | После | Ожидаемый результат |
|---|---|---|
| 4.1: «Отдел готовит отчёт ежемесячно» | 6.5: тот же текст в другом разделе | Соответствие найдено; показаны перенос и новый номер, а не удаление и добавление |
| 4.1: «Отдел готовит отчёт ежемесячно» | 6.5: «Отдел готовит отчёт ежеквартально» | Перенос и изменение; выделена точная замена периодичности |
| 4.1 остался на месте, но перед ним добавлен пункт | Прежний 4.1 стал 4.2 | Перенумерация, не самостоятельное перемещение |
| Соответствующего фрагмента нет | 6.6: новый текст без соответствия после всех проверок | Новый пункт, пустая сторона «до» |
| 4.2: текст без соответствия после всех проверок | Фрагмента нет | Удалённый пункт, пустая сторона «после» |
| Один пункт содержит два действия | Действия оформлены двумя пунктами | Разделение, а не два новых пункта |
| Два пункта | Один пункт сохраняет их содержание | Объединение, а не удаление одного из пунктов |
| Одинаковая строка под двумя разными заголовками | Одна такая строка | Проверка контекста; без достаточных оснований соответствие неоднозначно |
| Пункт отсутствует в результате ошибочного извлечения | Текст есть | Ограничение обработки, не подтверждённый новый пункт |

Итог этапа — проверяемая карта текстовых и структурных изменений между
редакциями. Она служит входом следующего подэтапа, где оценивается значение
изменений для организационной структуры, функций и ответственности.
