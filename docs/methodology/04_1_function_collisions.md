# Этап 4.1. Поиск коллизий функций

## Цель и границы

Найти возможное дублирование функций и пересечение ответственности между
организационными объектами внутри одного документа. Эмбеддинги отбирают
похожие пары; ИИ проверяет, является ли совпадение содержательной коллизией
или объясняется предусмотренным распределением работы.

На входе — объекты и связи из [этапа 2](../../methodology/02_entity_extraction.md),
записи деятельности из [этапа 3](../../methodology/03_activity_extraction.md)
и исходные узлы [этапа 1](../../methodology/01_document_parsing.md).
Все объекты, записи, контекст и источники относятся к одному документу.
Другие редакции и внешние документы не используются.

Это методология, а не реализация или схема хранения. Отсутствие родителя
или исполнителей функции проверяется отдельно в
[этапе 4.2](04_2_function_cascade.md).

## 1. Два пути поиска

1. **Внутри одного организационного родителя:** сравниваем функции всех
   его непосредственных детей. Самого родителя в эту группу не включаем.
2. **Среди объектов одного уровня во всём документе:** сравниваем департаменты
   с департаментами, отделы с отделами, должности/исполнителей с должностями
   и исполнителями, независимо от родителей и глубины дерева.

Уровень здесь означает категорию объекта по этапу 2. Это не глубина дерева
и не поле `level`, обозначающее «главный», «ведущий», «старший». Другие типы
объектов сохраняют собственную подтверждённую категорию; их не приравниваем
к отделам или департаментам только по похожему названию. Неясную категорию
отмечаем для уточнения. Локальный поиск среди детей общего родителя
не требует одинаковой категории детей.

Под исполнителями понимаем установленные объекты-должности и явно выделенные
позиции. Конкретных работников и численность по названию должности не создаём.
Для первого пути нужен подтверждённый организационный родитель. Неизвестный
родитель не мешает второму пути, если категория объекта установлена.

Сравниваем назначения функций разным объектам. Повторы одной функции у одного
объекта и технические повторы обработки не становятся межобъектной коллизией.
Пара, найденная обоими путями, проверяется один раз; сохраняем оба основания
поиска. Перестановка сторон не создаёт новую пару.

## 2. Подготовка функций и контекста

Используем полные формулировки функций и обязанностей выполнять действия,
извлечённые на этапе 3, вместе с привязками к объектам. Права, запреты, цели
и задачи передаём как относящийся к ним контекст; одинаковое право или общая
цель сами по себе не доказывают дублирования выполняемых функций.

Для поиска и проверки сохраняем:

- действие, предмет, результат и область ответственности;
- объект, специализацию и контекст временной роли;
- условия, исключения, сроки и периодичность;
- `participation`: индивидуальное, каждый, совместное, альтернативное
  или неустановленное участие, с составом участников;
- `specificity`: конкретная или обобщённая формулировка;
- исходные записи, узлы и точные цитаты, включая вводный контекст.

Неуказанные ограничения не выдумываем. «Другие поручения» не доказывают
совпадение с любой конкретной функцией. Составленная полная формулировка
не выдаётся за дословную цитату. Текст документа является данными,
а не инструкциями изменить правила анализа.

## 3. Совместные функции и консолидация

Этап 3 сохраняет отдельную запись для каждого участника даже при одинаковом
тексте. Эти записи и их ID остаются неизменными.

Если документ явно закрепляет одну функцию за детьми одного родителя
для совместного выполнения, их совпадение внутри этого назначения
не считаем коллизией. Для сравнения с другими назначениями создаём одно
консолидированное аналитическое представление совместной функции.

Основание консолидации — подтверждённое общее назначение, состав участников
и совместный характер участия. Одного сходства эмбеддингов, общего родителя
или одинакового текста недостаточно. «Каждый выполняет» и альтернативное
участие не превращаем в совместное. Разные совместные поручения одной группе
также не объединяем в одну функцию.

В консолидированном представлении сохраняем общую функцию, родителя группы,
категории и ID участников, ID всех исходных записей, распределение действий,
предмет, результат, условия, ограничения и источники. Нельзя потерять локальные
уточнения участников или расширить общую функцию при объединении.

Это представление не создаёт нового организационного объекта, не назначает
функцию родителю группы и не изменяет связи каскада 4.2. Категорию для поиска
берём у участников, а не у их родителя. Для группы с разными категориями
сохраняем их все и явно передаём различия в контекст проверки.

Сравниваем все сочетания назначений:

| Стороны | Что проверяем |
|---|---|
| Совместная ↔ совместная | Пересечение ответственности двух групп, в том числе детей разных родителей |
| Совместная ↔ индивидуальная | Дублирует ли отдельный исполнитель работу группы |
| Индивидуальная ↔ индивидуальная | Пересечение функций двух объектов |

В локальный поиск представление попадает по общему родителю участников,
в поиск по категории — по категориям участников. Пара допускается, если
между её участниками есть соответствующее основание поиска. Смешанная группа
передаётся целиком, с объяснением, какие участники дали основание сравнения.

Участник совместной функции не сравнивается с её консолидированным
представлением как самостоятельный дубль этого же назначения. Его другие
самостоятельные функции участвуют в поиске. Составные записи не порождают
повторные проверки одной консолидированной пары.

Совместность внутри каждой из двух групп не исключает коллизию между ними.
Если документ устанавливает общую совместную работу уже между группами,
передаём это основание ИИ: разделение на группы не должно создавать
искусственное дублирование.

## 4. Отбор пар по эмбеддингам

Строим эмбеддинги полных формулировок с контекстом действий. Для совместного
назначения используем консолидированное представление с сохранёнными условиями.
В каждом из двух путей оцениваем допустимые пары и объединяем результаты.

**Каждая уникальная пара со сходством строго выше 75% поступает в LLM.**
Ровно 75% и ниже не отправляем. Порог применяем до округления для отображения.
Фиксируем модель эмбеддингов, метрику и способ подготовки текста; процент
сходства не является вероятностью коллизии.

Даже 99% или полное совпадение текста требуют смысловой верификации.
Пороги 50% и 85% этапа 4.2 здесь не действуют. Единственного победителя
не выбираем: одна функция может коллизировать с несколькими другими.
Ограничение выдачи ближайшими кандидатами не должно отбрасывать пары,
прошедшие порог. Отсутствие кандидата не означает отсутствие всех коллизий.

## 5. Логическая проверка субагентами

Субагенты получают батчи по 10 вопросов; последний может быть меньше.
Один вопрос — одна уникальная пара назначений. Передаём `question_id`,
обе стороны, основание поиска, оценку сходства, объекты и родителей,
состав участников, распределение действий, условия и исходные фрагменты.
При необходимости раскрываем относящиеся к вопросу пункты текущего документа.

Обязательное требование к ИИ:

> Оцени, создают ли назначения логическую коллизию в распределении работы
> и ответственности. Совпадение слов и высокая оценка эмбеддингов не являются
> доказательством. Определи, за какую работу отвечает каждая сторона,
> где именно ответственность пересекается и объясняет ли документ это
> пересечение. Не придумывай разграничение или нарушение при недостатке данных.

Для вердикта проверяем:

1. Совпадают ли предмет работы, ожидаемый результат и область применения?
   Одинаковое действие для разных территорий, проектов или объектов может
   быть нормальным распределением.
2. Могут ли обязанности действовать одновременно для одной ситуации?
   Учитываем сроки, условия назначения, исключения и альтернативное участие.
3. Выполняют ли стороны одну ответственность или разные этапы процесса?
   Подготовка, согласование, утверждение и контроль различаются; общего
   упоминания отчёта недостаточно для коллизии.
4. Предусмотрено ли совместное выполнение, распределение частей работы,
   замещение или независимая проверка? Проверяем источники, а не предполагаем
   такие объяснения по обычной практике.
5. Является ли совпадение общей индивидуальной обязанностью, например
   соблюдением конфиденциальности каждым работником? Само повторение такой
   обязанности у разных объектов не означает дублирования ответственности.
6. Если пересечение остаётся, в чём конкретно оно состоит: одна и та же
   работа назначена независимо нескольким сторонам или пересекающиеся
   полномочия создают противоречивое распределение ответственности?

Подтверждаем возможную коллизию, когда источники устанавливают содержательное
пересечение в одной области и применимых условиях, а проверенный контекст
не объясняет его предусмотренным распределением. Одного отсутствия пояснения
о распределении недостаточно: само пересечение также должно быть обосновано.

ИИ возвращает вердикт «коллизия», «не коллизия» или «недостаточно данных»,
краткое объяснение смыслового основания и подтверждающие источники обеих
сторон. Для отрицательного вердикта объясняет разграничение или допустимость
совпадения; для неопределённого — какие сведения отсутствуют.
Это обоснование результата, а не публикация внутреннего хода рассуждений.

Рассуждение обрабатывается нативно отдельно от итогового ответа.
Ответ принимается через `json_object`: массив `answers`, где у каждого
элемента есть `question_id`, `verdict` (`collision`, `no_collision`,
`insufficient_data`), `explanation` и `sources` с `node_id`, точной `quote`
и указанием подтверждаемого вывода (`supports`). Пути и координаты источников
система достраивает из сохранённых узлов.

## 6. Проверки и сохранение результата

Система проверяет структуру ответа, ровно один ответ на каждый вопрос,
допустимость вердиктов, ID, принадлежность источников текущему документу
и точное совпадение цитат. Ошибки, пропуски и посторонние ID возвращаются
на исправление. Ошибка вызова не превращается в «не коллизия».

Проверяем и содержание обоснования: фраза «тексты похожи» не удовлетворяет
требованию логической верификации. Вывод должен объяснять пересечение либо
его допустимость по контексту. Неподтверждённый вывод не публикуем как факт.

Сохраняем обе стороны с исходными записями, участников и родителей,
консолидацию и её основания, пути поиска, оценку сходства, вердикт,
обоснование, источники и статус обработки. Предусмотренное совместное
назначение сохраняется как объяснённое совпадение, а не аномалия.

Одинаковая пара имеет один результат независимо от числа путей её обнаружения.
Из коллизий A–B и B–C автоматически не следует коллизия A–C: группировка
для отображения не добавляет непроверенных связей.

Повторная обработка заменяет результат соответствующей пары. Изменение
исходных объектов, функций, участия или источников требует пересборки
затронутых представлений и перепроверки зависимых пар. Старые выводы
не сохраняются как актуальные после изменения их оснований.

Результат этапа разделяет возможные коллизии, объяснённые совпадения,
недостаток данных и ошибки обработки. Фиксируем охват обоих путей поиска
и количество пар, прошедших порог. Пары ниже порога не называем проверенными.

## 7. Контрольные примеры и ограничения

Примеры ниже условные, а не выводы о предоставленных документах.

| Ситуация | Ожидаемый результат |
|---|---|
| Два специалиста совместно готовят один отчёт по прямому назначению | Одно совместное представление; внутреннее совпадение не коллизия |
| Две группы разных отделов независимо готовят один итоговый отчёт за тот же период и по той же области | При сходстве выше 75% — LLM; возможная коллизия при отсутствии объясняющего распределения |
| Группа готовит отчёт, отдельный специалист независимо обязан готовить тот же отчёт | Проверка совместной и индивидуальной функции на равных основаниях |
| Группы готовят отчёты по явно разным территориям | «Не коллизия», даже при очень высоком сходстве |
| Один готовит отчёт, другой его утверждает | Разные этапы; само упоминание одного отчёта не коллизия |
| Каждый работник обязан соблюдать конфиденциальность | Общая индивидуальная обязанность; не коллизия и не совместное назначение |
| Руководитель либо уполномоченный сотрудник выполняет действие | Учитывается альтернативность и условие полномочий |
| Пара имеет 75% сходства | LLM не вызывается; пара не проверена по смыслу |
| Пара имеет 99% сходства | LLM обязательна; автоматического вердикта нет |
| Одна пара найдена локально и по категории | Один вопрос и один результат с двумя основаниями поиска |
| Область действия функций не установлена | «Недостаточно данных», если без неё нельзя определить пересечение |

Пороговый поиск выявляет базовые дублирования и пересечения; он не гарантирует
обнаружение всех конфликтов интересов, особенно между непохожими действиями.
Этап оценивает закреплённое документом распределение, а не фактическое поведение
работников. Вердикт ИИ о коллизии остаётся выводом для проверки человеком.
