# ТЗ для разработки: ИИ-агент «Анализ организационной структуры и функционала»

Хакатон HackAlem AI. Команда: 3 человека (ML, методология, фронт). Разработка ведётся через ИИ-агентов.
Эталон интерфейса и формата данных: `visual_compare.html` (макет «Изменения → Визуал» с доказательной базой).

---

## 0. Как работать по этому ТЗ (для ИИ-агентов и команды)

1. Реализуй **строго по уровням приоритета** (раздел 8): P0 → P1 → P2 → P3. Следующий уровень начинается, только когда критерии приёмки текущего выполнены.
2. Каждый уровень должен давать **работающее демо**. Лучше меньше функций, но полностью рабочих.
3. Фронт и ML работают **параллельно через фикстуру** `fixtures/result.json` (раздел 5.3): фронт рисует по ней, ML выдаёт такой же JSON.
4. Правила из раздела 2 — **инварианты**. Нарушать их нельзя ни в одном уровне.
5. Если данных для вывода недостаточно, агент **не делает вывод**, а сообщает, чего не хватает.

## 1. Цель и сценарий

**Цель:** по двум документам («до» и «после» реорганизации) определить, что изменилось в структуре, и выдать проверяемые выводы: потерянные функции, дублирование, конфликт интересов, пересечение зон ответственности. Каждый вывод прослеживается до пункта исходного документа.

**Пользователь:** сотрудник, проводящий анализ организационных изменений.

**Сценарий:** загрузка двух документов → статус обработки → страница «Изменения» (Визуал / Word) → «Анализ» (находки по типам) → проверка находок (подтвердить / отклонить) → «Чат» для вопросов по документам.

**Проверка жюри:** контрольный комплект, где заранее известны реорганизация подразделения, потеря функции и дублирование. Проверяется, найдены ли они и указаны ли корректные источники.

## 2. Инварианты (обязательны на всех уровнях)

| # | Правило | Как обеспечить |
|---|---|---|
| I1 | Нет выводов без источника | Каждая находка содержит ≥1 источник с цитатой. Находка без источника не показывается. |
| I2 | Цитата дословная | `quote` должен находиться в тексте пункта `clause_id` (после нормализации пробелов и регистра). Валидатор проверяет это **кодом, не LLM**. Не прошла проверку — находка отбрасывается и пишется в лог. |
| I3 | Факт отделён от рассуждения | Шаги доказательства — либо `fact` (с цитатами), либо `inference` (рассуждение агента, помечается в UI). |
| I4 | Доказательство отсутствия | Для потерь и «создано» хранится, **что проверено**: область поиска, порог, ближайшие кандидаты со сходством. |
| I5 | Уверенность | Каждая находка имеет `confidence` (high / medium / low) и короткое основание. |
| I6 | Рекомендательный характер | В UI у каждой находки кнопки «Подтвердить / Отклонить» и дисклеймер о проверке сотрудником. |
| I7 | Только предоставленные документы | Внешние источники (НПА, операторы) используются только после загрузки пользователем или его явного подтверждения (P3). |

## 3. Архитектура

### 3.1. Пайплайн обработки

Запускается один раз после загрузки. Каждый этап обновляет статус задачи.

```
[1] Загрузка         → документы «до» и «после» сохранены
[2] Парсинг          → текст с сохранением структуры и нумерации пунктов
[3] Сегментация      → блоки (Структура, Положение, Кадры, ИБ…) и пункты с id
[4] Извлечение (LLM) → подразделения; функции с владельцем и ссылкой на пункт;
                        распорядительные действия (образовать / преобразовать / упразднить / слить)
[5] Сопоставление    → подразделения до↔после (статус); функции до↔после (эмбеддинги → LLM-проверка)
[6] Детекторы        → потеря, дублирование, конфликт интересов, пересечение зон
[7] Сборка доказательств → evidence для каждой находки
[8] Валидация        → проверка цитат (I2), отбрасывание невалидных
[9] Готово           → result.json
```

### 3.2. Правила детекторов

Пороги выносятся в конфиг, значения ниже — стартовые.

**Статус подразделения (must have 1)**
1. Если распорядительный пункт явно называет действие (образовать, преобразовать, упразднить, слить, переименовать) — статус по нему, источник = этот пункт.
2. Иначе: совпадение наименования → `kept`; есть в «до», нет в «после» → `abolished`; нет в «до», есть в «после» → `created` (с доказательством отсутствия похожих, I4).
3. Для каждого упразднённого или слитого подразделения определяется **правопреемник** (нужен для детектора потерь).

**Сопоставление функций**
1. Для функции из «до» берутся top-5 кандидатов из «после» по косинусному сходству эмбеддингов.
2. LLM проверяет, та ли это функция (да / нет / частично) с обоснованием.
3. Итог: совпала у того же владельца или правопреемника → `kept`; у другого владельца → `moved`; нет совпадения выше порога (0.75) → кандидат в `loss`.

**Потеря функции (must have 2)**
Функция в «до» закреплена за подразделением, в «после» не закреплена ни за кем. В evidence обязательно: исходный пункт, судьба подразделения-владельца, что проверено (I4).

**Дублирование (must have 3)**
В «после» две функции **разных** подразделений со сходством > 0.8, и LLM подтверждает, что это одна функция без разграничения ролей.

**Пересечение зон**
Разные подразделения, **один объект**, разные действия (согласует / устанавливает сроки / утверждает) без определённого порядка взаимодействия. По умолчанию `confidence: medium`.

**Конфликт интересов (must have 3)**
У **одного** подразделения или должности две функции над одним объектом, действия которых входят в несовместимую пару. Стартовый список пар (методолог дополняет):

| Действие A | Действие B |
|---|---|
| исполняет | контролирует / проводит аудит |
| закупает | принимает / приёмка |
| готовит отчёт | проверяет / утверждает отчёт |
| распределяет ресурсы | получает ресурсы |
| принимает решение | оценивает результат решения |

Дополнительно флагуется случай, когда контрольная функция **переехала** из независимого подразделения в подразделение-исполнитель (как аудит ИБ в эталоне).

**Противоречие функций** (метка рядом с конфликтом интересов)
Функции разных субъектов над одним объектом противоречат друг другу по смыслу. `confidence` не выше medium.

## 5. Модель данных

### 5.1. Пункт документа

```json
{
  "clause_id": "after:dibr:2.8",
  "doc": "after",
  "block": "Положение ДИБиР",
  "number": "2.8",
  "text": "Проводит аудит системы защиты информации…"
}
```

### 5.2. Находка / изменение

Одна запись = одна карточка в средней колонке Визуала и на страницах Анализа.

```json
{
  "id": "C-010",
  "type": "kept | transformed | created | abolished | moved | loss | duplication | conflict | contradiction | overlap",
  "block": "ИБ и режим",
  "title": "Конфликт интересов",
  "desc": "ДИБиР внедряет меры защиты и сам их проверяет",
  "from": ["f_audit"],
  "to": ["g_audit"],
  "also": ["g_prot"],
  "evidence": {
    "conclusion": "После реорганизации ДИБиР одновременно реализует меры защиты и проводит их аудит.",
    "method": "Правило несовместимости «исполняет — контролирует» для одного субъекта и одного объекта.",
    "steps": [
      {
        "kind": "fact",
        "text": "До реорганизации аудит ИБ проводила СВА.",
        "sources": [
          {"doc": "before", "block": "Положение СВА", "clause_id": "before:sva:2.5",
           "clause": "п. 2.5", "quote": "проводит аудит системы защиты информации", "item": "f_audit"}
        ]
      },
      {
        "kind": "inference",
        "text": "Объект обеих функций совпадает; исполнение и контроль оказались у одного субъекта.",
        "sources": []
      }
    ],
    "checked": {
      "scope": "Все 23 пункта документа «после»",
      "threshold": 0.75,
      "candidates": [{"label": "Пропускной режим", "clause": "п. 2.3", "score": 0.38, "item": "g_pass"}]
    },
    "npa": "НПА не загружены: вывод сделан только по документам.",
    "confidence": "high",
    "confidence_note": "Факты подтверждены цитатами; несовместимость — рассуждение агента."
  },
  "review": null
}
```

- `from` / `to` / `also` — id элементов левой и правой колонки (стрелки; `also` рисуется пунктиром).
- `checked` обязателен для `loss` и `created` (I4).

### 5.3. Результат задачи (`result.json`)

```json
{
  "job_id": "…",
  "summary": {"changed_blocks": ["Структура", "ИБ и режим", "IT"], "counts": {"loss": 1, "duplication": 1}},
  "conclusion": "Короткое итоговое заключение (3–6 предложений) по всем находкам",
  "blocks": [
    {"title": "Структура",
     "before": [{"id": "b_dib", "label": "Департамент ИБ", "status": "transformed", "clause_id": "…"}],
     "after":  [{"id": "a_dibr", "label": "Департамент ИБ и режима", "status": "transformed", "clause_id": "…"}],
     "changes": ["C-001", "C-002"]}
  ],
  "findings": { "C-001": { } }
}
```

**Фикстура:** `fixtures/result.json` собирается из демо-данных `visual_compare.html` и используется фронтом до готовности пайплайна.

## 6. Интерфейс

Верхнее меню: **Изменения · Анализ · Чат** (+ «Внешние факторы» на P3).
На каждой странице сверху: **краткое заключение** + «Показать полную аналитику» (раскрывает полный список выводов). Выгрузки в файл нет.

### 6.1. Загрузка
Два поля: «Документ До», «Документ После» (Word / PDF / Excel). Кнопка «Начать анализ».

### 6.2. Статус
Список этапов пайплайна (3.1) с состоянием: ожидает / идёт / готово / ошибка. По завершении — переход на «Изменения».

### 6.3. Изменения → Визуал (эталон: `visual_compare.html`)
- Сверху сводка: изменённые блоки и счётчики по типам.
- По каждому блоку три колонки: «до» | карточки изменений | «после».
- Стрелки: «до» → карточка → «после». Цвет по типу. Потеря — «∅ не закреплено».
- Наведение на карточку или пункт подсвечивает всю связку.
- Клик по карточке открывает **панель доказательной базы**: вывод → как получен → цепочка доказательств (цитаты кликабельны) → что проверено → нормативная база → уверенность → «Подтвердить / Отклонить».
- Бейджи статусов: для подразделений — создано / упразднено / сохранено / преобразовано; для функций — сохранено / перенесено / потеряна / создано.

### 6.4. Изменения → Word
Построчный дифф: удалённое зачёркнуто красным, добавленное зелёным. Переход из цитаты в панели доказательств открывает этот вид на нужном пункте с подсветкой.

### 6.5. Анализ
Подстраницы: **Потеря функций · Дублирование · Конфликт интересов** (метки «конфликт интересов» и «противоречие функций») · Пересечение зон. Каждая — список карточек-находок; клик открывает ту же панель доказательств.

### 6.6. Чат
Предустановленные запросы: «Что изменилось?», «Какие функции потеряны?», «Где дублирование?», «Насколько изменился штат?». Отвечает **только по пунктам документов** (RAG по `clauses`), каждое утверждение со ссылкой на пункт. Нет ответа в документах — прямо сообщает об этом и предлагает дозагрузить документ.

## 9. Тестирование

- **Контрольный комплект:** методолог заранее записывает ожидаемые находки (тип, подразделения, пункты) в `tests/expected.json`. Тест сверяет результат пайплайна.
- **Тест валидатора:** находка с изменённой цитатой должна отбрасываться.
- **Тест отсутствия:** на паре одинаковых документов — ноль потерь, ноль созданных.
- **Фронт:** все страницы открываются на `fixtures/result.json` без ошибок в консоли.
